tracer — a quantitative-goal-driven autonomous improvement loop

A separation-of-concerns design — loop (the re-entry vehicle) + external eval (pass/fail) + durable state (git/Issues) + gates — implemented directly as a single skill. The only command you type is /tracer. The skill reads the state and decides, every time, which of init / roadmap / advisor / patrol / completion to run.

An improvement's worker is not a long-lived session. The PM launches it as a throwaway subagent on each firing, and makes it write its results into Issues/PRs/the goal file. That's why everything can be restored on the next firing even after a /clear.

2. What happens with one command — automatic 5-state selection

When you type /tracer, the skill reads the state and runs only the first action that matches. Matching is top-down (A → E). It never runs multiple actions in the same cycle (to keep your unit of review to one).

A init
goals/ is empty, or there are 0 improvement files
Settle on one improvement target through dialogue. Fill in persona / metric / eval / baseline / target / deadline. Don't close until the measurement command actually runs
B roadmap
improvement exists but Phases is empty / Issues not filed
Write out every phase and file Issues for each (label:goal:<improvement>)
C advisor escalation
an improvement shows 0 metric improvement across the last 5 cycles of Log
Root-cause analysis with opus + effort max. Produces a proposed Issue (read-only, does not implement)
D routine patrol
an active improvement has open Issues
Per improvement: measure the metric → dispatch one Issue → independent verification → phase decision
E completion report
all active improvements have hit their target
Mark the improvement inactive and drop it from the loop. Suggest what to start next
Priority is strictly top-down. For example, if "open Issues remain but the metric hasn't moved for 5 cycles," C runs instead of D. The design intent: revisit the plan itself before working on Issues.

3. Reward is two-layered — qualitative goals are rejected (RLVR-style)

micro reward — eval

Pass/fail gate for one Issue

  • A deterministic command (e.g. npm test && npm run lint)
  • exit 0 = pass. The worker's self-report is not accepted
  • No PR/merge without a pass (a regression-prevention gate)
macro reward — metric

The goal metric itself

  • e.g. 42 errors/week → 20 or fewer (with a deadline)
  • Measured every patrol and recorded as a time series in the goal file
  • Phase completion is judged by metric movement, not by the number of Issues closed
Closing all the Issues but the metric not moving is not "a failure of the work" — it's a "the plan is wrong" signal. On the next firing the state check flows to C instead of D, and the advisor restructures the Issues. This is the core of self-improvement.

4. Inside routine patrol (D)

For each active improvement, it goes through: restore state → measure → dispatch → independent verification → phase decision → dashboard update + brief report. It rebuilds from the goal file from scratch every time, not from conversation memory.

Restore stateRe-read the goal file and decision log from scratch every time. Don't rely on conversation memory (a guard against context exhaustion).
Measure the metricTake the number every patrol and append it to the goal file's Log. If measurement is broken, escalate instead of working.
Dispatch (one Issue per improvement)Hand the worker the persona, eval, and past failure logs, and let it run autonomously in a worktree. Multiple improvements run in parallel.
Independent verificationConfirm pass/fail in two stages — tamper check + a separate verifier (§5).
verification passes + eval passes → PR (L0: you decide the merge / L1+: the PM merges) fail → record attempt n/5 in an Issue comment, retry on the next firing 5 failures → escalation + that Issue is frozen
Phase decisionAll Issues closed + metric improved → advance to the next phase. Metric stalled → redirect to C on the next firing. Target reached → go to E on the next firing.
Dashboard update + brief reportRegenerate dashboard.html (§8) and give you a few-line summary. Keep details in the PR/Issue/dashboard and keep chat thin.

5. Independent verification — never advance on the worker's self-report

Two verification stages sit before the pass-handling. A worker merely claiming "eval passed" does not move the PR forward, and indirect tampering with the reward function (eval / metric calculation / truth) is stopped mechanically. The verifier is a subagent separate from the implementing worker, whose job is to independently re-confirm pass/fail.

tamper check

Cross-check the diff against protected_paths

  • Take git diff --name-only origin/main...<branch>
  • Cross-check against the goal file's repo.protected_paths
  • If even one file hits, ignore the eval result and escalate
separate verifier

A different subagent re-runs eval on the PR branch

  • Launch a subagent different from the implementing worker
  • Have it check out the PR branch and re-run eval
  • Confirm pass/fail independently (not dependent on the self-report)
The path by which the side earning the reward rewrites the side computing the reward is blocked with a mechanical check — not a "do not" sentence in the prompt.

What protected_paths covers, and the worker prohibitions

  • protected_paths: the eval execution code / metric calculation scripts / truth data / validation around the gate. Listed in the goal file's repo.protected_paths
  • Banning baseline-swap flags: don't let the worker use flags that rewrite the acceptance criteria, e.g. --accept-new-baseline
  • If genuinely needed, the worker doesn't implement — it writes the necessity in an Issue comment and stops (changes only via user approval)

6. Staged delegation of judgment — the PM earns authority through a track record

The PM's authority is not fixed; it widens in stages based on a track record of agreement. It starts by consulting on everything (L0), and after the recommendation matches the actual decision 5 times in a row it is promoted one step.

L0 — consult on everything (initial) You decide escalations and merges. But the PM is obliged to attach a "recommendation + concerns" every time.
→
L1 — decide + report after The PM decides and acts, then reports in the next brief. You retain a veto.
→
L2 — record only Logged in the decision log and rolled up into a weekly summary.
  • Promotion condition: the PM's recommendation matches your actual decision 5 times in a row → the PM proposes promotion, you approve
  • One mismatch resets the streak count to 0
  • The audit trail is _pm/decisions.md. You can judge "is it OK to delegate" by numbers, not gut feel
  • Autonomy is per repo × improvement

Exception: the reward function is never delegated

Changing the definition of eval: / metric: requires your approval even at L2. If the PM could loosen its own acceptance criteria, the whole loop would be rendered meaningless by reward hacking.

On top of that, diffs touching repo.protected_paths (eval/metric/truth calculation paths) are detected mechanically by the independent verification in §5, blocking indirect tampering from the worker.

7. Deep advisor consultation (C) — opus + effort max

The technical-advisor escalation uses "opus + effort max." effort max allocates the maximum thinking budget (switch with /effort max). The key is confining max to "thinking only." Running implementation at max blows up both tokens and wall-clock, so use it in separated layers.

effortuse
lowboilerplate short answers / light classification
medium (default)routine patrol / PM direction / dispatching implementation
highinvolved design decisions / multi-file reviews
xhighisolating hard bugs / proposing larger refactors
maxadvisor consultation only. Root-cause analysis of stalls and proposing alternative approaches
effort is inherited from the parent session into subagents. The procedure is /effort max → launch the advisor subagent (model: opus) → return to /effort medium when done. Don't leave max sitting on.
Advisor (opus + max) Read-only. Produces root-cause analysis and alternative approaches. The exit is a proposed Issue. Does not implement.
→
PM (opus + medium) Takes the advisor's proposed Issue, decomposes it, and dispatches workers. Directs the implementation.
→
Worker (sonnet) Implements code and tests in a worktree. max is not used for implementation.
The trigger is decision C in §2 (0 metric improvement across the last 5 cycles of Log), or hitting attempt 5/5 during routine patrol. Only once per stall situation. If no proposal emerges even then, raise it to the user via normal escalation. Whether to file is governed by autonomy — the advisor never files an Issue directly (L0: approval, L1+: the PM files).

8. dashboard — intervention and explanation surface

At the end of every cycle, the PM regenerates .claude/goals/_pm/dashboard-<improvement>.html. You look at this to decide whether to step in. The brief report just puts that full path at the top; the details are consolidated on the dashboard side.

8.1 Two intended readers

The dashboard is designed not as a state viewer but as "a tool the engineer pulls up while explaining to their manager."

PersonaSituationHow they use the dashboard
A: engineer (vibe coder)One person running 5–10 parallel improvements through AI. Light on specs, doesn't read code closely, result-drivenOpens it every morning. Catches up on "what moved overnight" and "what needs my approval"
B: manager (PM/PO)Can't read code or PRs, but understands structure at a PM/PO level. Not inside the chat session, doesn't run AI themselvesDoes not open it directly. Looks at it together with A during explanations, to decide direction and schedule

8.2 The six questions the dashboard answers

If "what's happening, what improves, when it improves" are unclear, A can't track it themselves and B can't plan around it. The dashboard answers these six.

  • ① metric position and distance to target: a single line like 350ms → 310 → ≤20. This is the real progress signal
  • ② WHAT: what is moving in this improvement right now (one sentence, avoid engineer jargon)
  • ③ WHEN: when it lands (ETA, remaining cycles, stall warning)
  • ④ awaiting intervention: PR merge decisions, L0 escalation proposals, advisor Issue proposals — all in one place
  • ⑤ delta since yesterday: one-line summary (1 PR merged · metric +5% · no ask)
  • ⑥ per-phase before/after diagrams: per roadmap phase (= Issue group / epic), both a C4 subset and a workflow diagram. The AI generates a draft and A corrects it
persona (whose pain, = WHY) is obvious to both A and B, so it's dropped from the hero. Issue count and PR count are noise to B, so they're demoted to secondary information. The shared language is metric × before/after diagram.

The per-phase before/after diagram always pairs a C4 subset with a workflow diagram (sequence / user journey). The former captures the structural delta, the latter the behavioral delta. 8.5 "Look and decide whether to intervene" is the real operation

Not "hand off the work and never look," but "look at the dashboard and decide whether to intervene" — that is the user-side operation of this skill. The brief report is the entry point; the dashboard is the real thing. And the real purpose of the dashboard is the scene where A explains to B: building a shared language between the two.

9. Self-improvement runs in three layers

This loop's self-improvement happens in three places at once. Workers learn from failure logs, the PM restructures the plan from the metric, and the harness itself is updated by the decision-match rate.

LayerMechanismWhat improvesReward signal
L1 worker Accumulates failure reasons in Issue comments → the next attempt reads them and takes a different approach the deliverable eval (pass/fail)
L2 plan Metric stalls → redirected to state decision C, and the advisor redesigns the Issues the plan metric (the number)
L3 PM Decision matching → autonomy promotion / recurrence of the same failure type → proposals to fix the persona and phase definitions (approval required) the PM's judgment & the harness itself decision-match rate

10. Works in any repo

  • The skill ships as a plugin (installed via the plugin marketplace), state is in each repo's .claude/goals/. State never mixes across repos
  • At init it detects and records the repo's machinery: worktree (use make wt-start etc. if present, otherwise git worktree), implementation-flow skill (follow an issue-implement-style skill if present)
  • The autonomy track-record count is also per repo × improvement

Summary

  • The only command you type is /tracer. The skill reads the state and runs one of five states (init / roadmap / advisor / patrol / completion)
  • Your job is "look at the dashboard, and give feedback / unblock when it gets stuck." Setup dialogue and merge / escalation answers also go through this one command
  • The PM treats only "did the number move" as truth, and never advances on the worker's self-report
  • All memory lives in git / Issues / the goal file, so patrols survive even when the session is cut
  • The PM's authority widens in stages based on a track record of agreement (5 in a row). But the acceptance criteria stay yours forever
  • The acceptance criteria and measurement code (repo.protected_paths) are protected from the worker. Indirect tampering is also blocked by a mechanical check
