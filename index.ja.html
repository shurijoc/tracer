tracer — 定量ゴール駆動の自律改善ループ

「loop（再発火の器）＋外部 eval（合否）＋durable state（git/Issue）＋ゲート」の分離設計を、そのまま 1 つの skill に実装したもの。あなたが打つコマンドは /tracer ただ 1 本。skill が state を読んで、init / roadmap / 顧問 / 巡回 / 完了 のどれを実行すべきかを毎回判定する。

1. 全体像 — あなたが打つのは /tracer だけ

ユーザー
⇅ 対話の入口はこのコマンド 1 本（init 対話・escalation 回答・merge 判断もここに集まる）
/tracer
↓ skill が state を読み 5 状態 (A〜E) から 1 つ選んで実行
PM (tracer)
↓ 通常巡回 (D) では improvement 毎の作業 1 件ずつを並列 dispatch（worktree 隔離）
bugfix workerpersona+eval を注入
perf workerpersona+eval を注入
kpi workerpersona+eval を注入
durable state（PM の記憶はここ。session の context に依存しない） 各 repo の .claude/goals/<improvement>.md ／ GitHub Issue・PR ／ git 履歴 ／ _pm/decisions-<improvement>.md・activity-<improvement>.md
毎サイクル末に dashboard を再生成（介入判断の窓） .claude/goals/_pm/dashboard-<improvement>.html ／ あなたはこれを見て介入・テコ入れする
improvement の worker は常駐セッションではない。PM が発火のたびに使い捨ての subagent として起動し、結果は Issue/PR/goal file に書き残させる。だから /clear しても次の発火で全部復元できる。

2. 1 コマンドで何が起きるか — 5 状態の自動判定

/tracer を打つと、skill は state を読み 最初にマッチした action を 1 つだけ実行する。判定は上から順 (A → E)。同サイクルに複数 action は走らせない (あなたの確認単位を 1 つに保つため)。

A init
goals/ が空 or improvement file 0 件
改善対象を 1 つ対話で確定。persona / metric / eval / baseline / target / 期限を埋める。計測コマンドが実際に動くまで閉じない
B roadmap
improvement あるが Phases 空 / Issue 未起票
全フェーズを書き切り、各フェーズで Issue 起票 (label:goal:<improvement>)
C 顧問 escalation
直近 5 サイクル分の metric Log で改善 0 の improvement あり
opus + effort max で原因分析。Issue 起票案を出す（読み専、実装はしない）
D 通常巡回
active improvement で open Issue がある
improvement 毎に metric 計測 → Issue 1 件 dispatch → 独立検証 → フェーズ判定
E 完了報告
全 active improvement が target 達成
improvement を inactive 化、ループから外す。次に何を始めるか提案
優先順は厳密に上から。たとえば「open Issue は残ってるが metric が 5 サイクル動かない」なら、D ではなく C が走る。Issue を作業する前に計画自体を見直す、が設計意図。

3. 報酬は 2 層 — 定性ゴールは受け付けない (RLVR 的)

micro 報酬 — eval

Issue 1 件の合否ゲート

  • 決定論的コマンド（例: npm test && npm run lint）
  • exit 0 = 合格。worker の自己申告は採用しない
  • 合格しないと PR/merge に進めない（回帰防止ゲート）
macro 報酬 — metric

ゴール指標そのもの

  • 例: エラー 42 件/週 → 20 件以下（期限つき）
  • 巡回毎に計測して goal file に時系列記録
  • フェーズ完了の判定基準は Issue 消化数ではなく metric の動き
Issue を全部閉じたのに metric が動かない＝「作業の失敗」ではなく「計画の誤り」シグナル。次の発火で状態判定が D ではなく C に流れ、顧問が Issue を組み直す。ここが自己改善の核。

4. 通常巡回 (D) の中身

active improvement 毎に以下を踏む。state 復元 → 計測 → dispatch → 独立検証 → フェーズ判定 → ダッシュボード更新 + 短報。会話の記憶ではなく goal file から毎回ゼロから組み立てる。

state 復元goal file・判断ログを毎回ゼロから読み直す。会話の記憶に頼らない（context 枯渇対策）。
metric 計測巡回のたびに数値を取り、goal file の Log に追記。計測が壊れていたら作業せず escalation。
dispatch（improvement 毎に Issue 1 件）worker に persona・eval・過去の失敗ログを渡して worktree で自走させる。複数 improvement は並列。
独立検証tamper check + verifier 分離の 2 段で合否を確定（§5）。
独立検証 pass + eval 合格 → PR（L0: merge はあなたが判断 / L1+: PM が merge） 不合格 → 試行 n/5 を Issue コメントに記録、次の発火で再挑戦 5 回失敗 → escalation + その Issue は凍結
フェーズ判定Issue 全消化 + metric 改善 → 次フェーズへ。metric 停滞 → 次の発火で C にリダイレクト。target 達成 → 次の発火で E へ。
dashboard 更新 + 短報dashboard.html を再生成（§8）し、あなたに数行のサマリ。詳細は PR・Issue・dashboard に置き、チャットは薄く保つ。

5. 独立検証 — worker の自己申告で前進しない

合格処理の前に検証を 2 段で挟む。worker が「eval 通った」と言うだけでは PR は進まず、報酬関数 (eval / metric 計算 / truth) への間接改変も機械的に止める。verifier = 実装 worker とは別の subagent で、合否を独立に再確認する役。

tamper check

diff を protected_paths と突合

  • git diff --name-only origin/main...<branch> を取る
  • goal file の repo.protected_paths と突合
  • 1 ファイルでも hit したら eval 結果を無視して escalation
verifier 分離

別 subagent が PR branch 上で eval 再実行

  • 実装 worker と別の subagent を起動
  • PR branch を check-out させて eval を再走
  • 合否を独立に確認 (自己申告に依存しない)
reward を稼ぐ側が reward を計算する側を書き換える経路を、プロンプトの禁止文ではなく機械チェックで遮断する。

protected_paths の対象と worker 禁則

  • protected_paths: eval 実行コード / metric 計算スクリプト / truth データ / gate 周りの validation。goal file の repo.protected_paths に列挙
  • baseline 差替 flag の禁止: --accept-new-baseline 等、合格基準を書き換える flag は worker に使わせない
  • 必要があれば worker は実装せず Issue コメントに必要性を書いて終了 (ユーザー承認経由でのみ変更可)

6. 判断の段階委譲 — PM は実績で権限を獲得する

PM の権限は固定ではなく、判断一致の実績で段階的に広げる。最初は全件相談 (L0)、5 回連続で推奨案と実決定が一致したら 1 段昇格する。

L0 — 全件相談（初期値） escalation・merge はあなたが決める。ただし PM は毎回「推奨案 + 懸念」を添える義務がある。
→
L1 — 即決 + 事後報告 PM が決めて実行し、次の短報で報告。あなたには拒否権が残る。
→
L2 — 記録のみ 判断ログに残し、週次サマリに集約。
  • 昇格条件: PM の推奨案があなたの実決定と連続 5 回一致 → PM が昇格を提案、あなたが承認
  • 不一致が 1 回出たら連続カウントは 0 に戻る
  • 突合の証跡は _pm/decisions.md。「委譲してよいか」を感覚でなく数字で判断できる
  • autonomy は repo × improvement 単位

例外: 報酬関数だけは絶対に委譲しない

eval: / metric: の定義変更は autonomy が L2 でもあなたの承認必須。PM が自分で合格基準を緩められると、ループ全体が reward hacking で無意味化するため。

さらに repo.protected_paths (eval/metric/truth 計算 path) への diff は §5 の独立検証で機械的に検出し、worker からの間接改変も遮断する。

7. 深掘り顧問相談 (C) — opus + effort max

技術顧問エスカレーションは「opus + effort max」で行う。effort max は思考予算を最大に振る指定 (/effort max で切替)。max を「思考専用」に閉じ込めるのが肝。max で実装まで走らせるとトークンも壁時計も爆発するので、レイヤを分けて使う。

effort用途
low定型の short answer / 軽い分類
medium (default)通常巡回・PM 指揮・実装差配
high込み入った設計判断・複数ファイル横断レビュー
xhigh難バグの原因切り分け・大きめのリファクタ案出し
max顧問相談専用。停滞局面の原因分析と別アプローチ立案
effort は親セッションから subagent に継承される。手順は /effort max → 顧問 subagent (model: opus) 起動 → 終わったら /effort medium に戻す。max を素のまま放置しない。
顧問 (opus + max) read-only。原因分析と別アプローチを出す。出口はIssue 起票案まで。実装はしない。
→
PM (opus + medium) 顧問の起票案を受けて Issue 分解と worker 差配。実装の指揮を取る。
→
実働 (sonnet) worktree でコード実装・テスト。max は実装に使わない。
発動条件は §2 の判定 C (直近 5 サイクル分の Log で metric 改善 0)、または通常巡回中に試行 5/5 到達。同一停滞局面につき1 回だけ。それでも案が出ない場合は通常 escalation でユーザーに上げる。起票の可否は autonomy に従い、顧問は直接 Issue を立てない (L0 は承認、L1+ は PM が起票)。

8. dashboard.html — あなたの介入窓口

毎サイクル末、PM は .claude/goals/_pm/dashboard.html を再生成する。あなたはこれを見て介入・テコ入れを判断する。短報はそのフルパスを冒頭に出すだけで、詳細はダッシュボード側に集約する。

今サイクル: D — 通常巡回 · 直近 stalled なし、active 全て open Issue あり
bugfix ●
42 → 38 → target ≤20
P2 (3/5) · L0 (2/5 一致)
perf ●
350ms → 310ms → target ≤200ms
P1 (4/4) · L1 (5/5 → L2 昇格提案中)
◆ 介入候補: #21 perf PR (L0 merge 判断待ち) · perf autonomy 昇格提案
次回予想: D (open Issue 残あり)

含む情報:

  • 今サイクルの現在地: 走らせた action (A〜E) と判定理由
  • improvement 毎のカード: metric 推移 sparkline・現フェーズ進捗・凍結 Issue・autonomy level と判断突合の現状
  • 介入候補セクション: ユーザーに判断を仰ぎたい項目 (L0 escalation 案・顧問起票案・merge 待ち PR)
  • 次回 /tracer の予想 action: 次サイクルが A〜E のどれに当たりそうか
作業を任せて見ない、ではなく 「ダッシュボードを見て介入判断する」 がこの skill のユーザー側の運用。短報はその入口、dashboard が本体。

9. 自己改善は 3 層で回る

このループの自己改善は 3 ヶ所で同時に起きる。worker は失敗ログから学び、PM は metric で計画を組み直し、harness 自体も判断一致率で更新される。

層仕組み改善対象報酬シグナル
L1 worker 失敗理由を Issue コメントに蓄積 → 次の試行はそれを読んで別アプローチ 成果物 eval (合否)
L2 計画 metric 停滞 → 状態判定 C にリダイレクトされ顧問が Issue を再設計 計画 metric (数値)
L3 PM 判断突合 → autonomy 昇格 ／ 同型失敗の再発 → persona・フェーズ定義の修正提案（要承認） PM の判断・harness 自体 判断一致率

10. どの repo でも使える

  • skill は global（~/.claude/skills/tracer/）、state は各 repo の .claude/goals/。repo を跨いで state は混ざらない
  • init 時に repo の機構を検出して記録: worktree（make wt-start 等があれば利用、なければ git worktree）、実装フロー skill（issue-implement 系があれば踏襲）
  • autonomy の実績カウントも repo × improvement 単位

まとめ

  • あなたが打つコマンドは /tracer ただ 1 本。skill が state を読み 5 状態 (init / roadmap / 顧問 / 巡回 / 完了) から 1 つを実行する
  • あなたの仕事は 「ダッシュボードを見て、詰まったら FB・テコ入れする」。設定対話と merge / escalation 回答もこの 1 コマンド経由
  • PM は「数値が動いたか」だけを真実として扱い、worker の自己申告では前進しない
  • 記憶は全部 git / Issue / goal file にあるので、session が切れても巡回は壊れない
  • PM の権限は判断一致の実績（連続 5 回）で段階的に広がる。ただし合格基準だけは永久にあなたのもの
  • 合格基準と計測コード (repo.protected_paths) は worker から守る。機械チェックで間接改変も遮断する
